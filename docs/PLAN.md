# پلن اجرایی — نسخه ۲ (پنل وب + انتخاب محدوده روی نقشه)

تاریخ: ۱۴۰۵/۰۶/۲۴ (2026-09-15)
جایگزین نسخه‌ی ۱. مبنا: دموی فعلی (`divar_demo/`) + نقشه‌ی API در `docs/DIVAR_API.md`.

## چه چیزی نسبت به نسخه‌ی ۱ عوض شد و چرا

| قبل | حالا | دلیل |
|---|---|---|
| بات تلگرام رابط کاربر | **پنل وب** رابط کاربر؛ تلگرام فقط اطلاع‌رسانی | فرم چندمرحله‌ای و نقشه در تلگرام بد است |
| انتخاب محله با نام | **کشیدن محدوده روی نقشه** (محله با نام هم می‌ماند) | دیوار `bbox` را بومی می‌پذیرد — تست شد |
| صفحه‌ی جزئیات برای هر آگهی | ‏`mapview/viewport`: ۲۰۰ آگهی با متراژ/اتاق/سن/امکانات/مختصات در **یک** درخواست | مشکل ۴۲۹ برای جریان اصلی حذف می‌شود |
| موازی‌سازی جزئیات، گام اصلی | فقط برای N آگهی برتر، به‌صورت تنبل | دیگر گلوگاه نیست |

ترتیب جدید:

```text
۰. اصلاح‌های کوچک از کشف API                     نیم ساعت
۱. Collector نسخه ۲: نقشه‌ای + محدوده              ۲-۳ ساعت
۲. کش و تاریخچه روی SQLite                          ۲ ساعت
۳. پنل وب: نقشه + فیلترها + جدول رتبه‌بندی          ۱-۲ روز
۴. جزئیات تنبل + موازی‌سازی محدود                   ۲ ساعت
۵. اطلاع‌رسانی تلگرام (فاز بعد)                     نیم روز
```

## گام ۰ — اصلاح‌های کوچک از کشف API

- ‏`rooms` با کلمه‌ی فارسی (`["دو","سه","چهار","پنج یا بیشتر"]`) — الان `number_range`
  می‌فرستیم و دیوار بی‌صدا نادیده می‌گیرد. فیلتر محلی می‌ماند (دفاع دوم).
- ‏`parking` / `elevator` / `warehouse` / `balcony` به‌صورت `boolean` به API.
- ‏`--owner-only` → `business-type: ["personal"]`.

**تأیید:** برای هر فیلتر diff مجموعه‌ی توکن‌ها با و بدون فیلتر. با `--rooms 3` هیچ
«یک‌خواب» در نتایج نباشد.

## گام ۱ — Collector نسخه ۲: نقشه‌ای + محدوده

**چه:**

- تابع جدید `search_map(city_id, bbox, filters)` در `collector.py` که
  `POST /v8/mapview/viewport` را می‌زند و هر آگهی را به این شکل برمی‌گرداند:

```text
token, title, lat, lon, approximate_location,
size, rooms, age_years, has_parking, has_elevator, has_storage,
deposit_rounded, rent_rounded, image_url
```

  متراژ/اتاق/سن از `chips[].title` با regex؛ امکانات از نام فایل آیکون (`parking.png` …).
- **تقسیم محدوده:** اگر `count > 200`، محدوده به ۴ ربع تقسیم می‌شود و بازگشتی ادامه
  می‌یابد تا هر خانه ≤ ۲۰۰ باشد. سقف عمق ۵ (۱۰۲۴ خانه) — بیشتر از آن یعنی محدوده‌ی
  کاربر بیش از حد بزرگ است؛ پیام بده. توکن‌های تکراری در مرز خانه‌ها با `set` حذف می‌شوند.
- **قیمت دقیق:** `price_fields` گردشده است («۳ میلیارد»). برای رهن معادل به عدد دقیق
  نیاز داریم. راه: همان محدوده را یک بار هم با `POST /postlist/w/search` + فیلد
  `bbox` (صفحه‌بندی ۲۴تایی) بگیر و روی `token` join کن — ارزان، بدون ۴۲۹.
  اگر توکنی فقط در نقشه بود، قیمت گردشده با پرچم `price_is_rounded=True` نگه داشته شود.
- **چندضلعی:** API فقط مستطیل می‌فهمد. اگر کاربر چندضلعی کشید، bbox آن به API می‌رود
  و بعد نقاطی که بیرون چندضلعی‌اند با point-in-polygon (ray casting، ۱۵ خط، بدون
  وابستگی) حذف می‌شوند. پین‌های `approximate_location=True` با تلورانس ~۲۰۰ متر.
- **محله‌های داخل محدوده (نمایشی):** از `data/districts_tehran.json` محله‌هایی که
  مرکزشان داخل چندضلعی است → به‌عنوان چیپ نمایش داده می‌شوند و در `snapshots` ذخیره
  می‌شوند (برای مقایسه‌ی بعدی). این «هر محله‌ای که تو محدوده بود» را پوشش می‌دهد بدون
  اینکه جستجو به مرز محله‌ها محدود شود.
- ‏`normalize()` باید از دو منبع (لیست/جزئیات و کارت نقشه) بتواند رکورد بسازد.
  فیلدهایی که کارت نقشه ندارد (طبقه، سال دقیق ساخت، قابل تبدیل، توضیحات) `None`
  می‌مانند تا گام ۴.

**تأیید:**
- محدوده‌ی اختیاریه با `size 80-150` → تعداد نتایج برابر `count` دیوار (۸۲۲ در تاریخ تست) ± ۵٪.
- محدوده‌ی بزرگ (۵ کیلومتر) → تقسیم بازگشتی، صفر توکن تکراری، صفر ۴۲۹.
- چندضلعی مثلثی → هیچ پینی بیرون مثلث نباشد.
- اندازه‌گیری و ثبت محدودیت نرخ `mapview` در `DIVAR_API.md` (تا الان ناشناخته).

## گام ۲ — کش و تاریخچه روی SQLite

بدون تغییر نسبت به نسخه‌ی ۱ به‌جز اینکه `snapshots` لات/لانگ و منبع (`map`/`list`) هم
ذخیره کند. **SQLite با `sqlite3` استاندارد**؛ مهاجرت به PostgreSQL بعداً فقط تعویض
connection است.

```sql
posts     (token PK, first_seen, last_seen, lat, lon, detail_json, detail_at)
snapshots (token, seen_at, deposit, monthly_rent, size, rooms, district, source,
           PRIMARY KEY (token, seen_at))
searches  (id PK, name, params_json, created_at, last_run_at, notify_chat_id)
```

- هر اجرا: برای هر آگهی یک snapshot، `last_seen` به‌روز، `first_seen` برای جدیدها.
- ستون «تغییر قیمت» در خروجی = رهن معادل الان نسبت به اولین snapshot.
- ‏«جدید» = `first_seen` در همین اجرا. این دو ستون در پنل و در اطلاع‌رسانی تلگرام
  اصل کار هستند.

**تأیید:** دو اجرای متوالی → هر توکن دو ردیف snapshot؛ اجرای دوم زیر ۵ ثانیه از کش.

## گام ۳ — پنل وب

**اصل:** بدون React، بدون auth، روی `localhost`. یک صفحه، FastAPI پشتش.

**استک:**
- ‏FastAPI + uvicorn (از استک سند).
- پوسته: **TailAdmin** نسخه‌ی HTML (مخزن `tailadmin-free-tailwind-dashboard-template`،
  مجوز MIT، Tailwind v4). سایدبار، هدر، کارت‌های آمار، جدول و فرم‌هایش را
  برمی‌داریم؛ صفحات نمونه‌اش (کالندر، پروفایل، چارت‌ها) را برنمی‌داریم.
- نقشه: **Leaflet** + **Leaflet.draw** از CDN، کاشی OpenStreetMap.
  (کاشی‌های نشان که دیوار می‌زند کلید می‌خواهد؛ OSM برای شروع کافی است.)

**سه نکته‌ی واقعی درباره‌ی TailAdmin که باید از اول تکلیفشان روشن باشد:**

۱. **مرحله‌ی build لازم دارد.** Tailwind v4 کلاس‌های استفاده‌نشده را حذف می‌کند، پس
   نمی‌شود CSS آماده‌اش را برداشت و کلاس دلخواه نوشت. ولی به webpack خودش نیاز نداریم:
   ‏`style.css` آن یک فایل استاندارد Tailwind v4 است (`@import "tailwindcss"` + `@theme`)،
   پس با CLI رسمی کامپایل می‌شود:

```bash
npx @tailwindcss/cli -i web/static/css/style.css -o web/static/css/app.css --watch
```

   یک بار `--watch` در ترمینال کنار uvicorn، تمام.

۲. **راست‌به‌چپ از قبل پشتیبانی می‌شود.** (فرض اولیه‌ی من غلط بود — بررسی شد.)
   قالب ۳۳۷ کلاس `rtl:` در HTML و چند قاعده‌ی `[dir="rtl"]` در CSS دارد و
   ‏`js/i18n.js` خودش `document.documentElement.dir` را ست می‌کند. برای ما کافی است
   ‏`<html dir="rtl">` بگذاریم؛ نیازی به بازنویسی کلاس‌ها نیست.

۳. **فونت.** پیش‌فرضش Outfit از Google Fonts است که هم لاتین است هم ممکن است در
   ایران باز نشود. جایگزین: **Vazirmatn** به‌صورت فایل محلی در `web/static/fonts/`
   و `--font-outfit` در `@theme` به آن اشاره کند — بدون تغییر بقیه‌ی تمپلیت.

**ساختار:**

```text
web/
  app.py                  FastAPI: سرو صفحه + endpointها
  static/
    index.html            صفحه‌ی اصلی: سایدبار + فیلترها + نقشه + جدول
    css/style.css         استایل TailAdmin + @source + تغییر فونت  (ورودی build)
    css/app.css           خروجی کامپایل‌شده  (در git نادیده گرفته شود)
    js/app.js             نقشه، فرم، جدول، polling
    fonts/                Vazirmatn
  vendor/tailadmin/       کلون مخزن، فقط برای برداشتن قطعه‌ها — سرو نمی‌شود
divar_demo/
  search.py               run_search(params) -> results
                          (از main.py بیرون کشیده می‌شود؛ CLI و وب هر دو صدایش می‌زنند)
```

**endpointها:**

```text
GET  /                        صفحه
GET  /api/districts           کاتالوگ محله‌ها (نام، id، مرکز) برای پیشنهاد و چیپ‌ها
POST /api/search              {polygon | bbox | district_ids, filters, weights?}
                              → {results[], median, count, districts_in_region[],
                                 suspicious[], run_id}
GET  /api/post/{token}        جزئیات تنبل (گام ۴)
```

**رابط:**

```text
┌──────────────────────────────┬───────────────────────────────────┐
│ فیلترها                      │                                   │
│  متراژ [80]-[150]            │           نقشه (Leaflet)           │
│  اتاق  ○۱ ●۲ ○۳ ○۴+          │   ابزار: مستطیل / چندضلعی / پاک   │
│  سقف ودیعه [   ] م           │   پین‌ها رنگی بر اساس «٪ نسبت به   │
│  سقف اجاره [   ] م           │   بازار» (سبز ارزان، قرمز گران)    │
│  ☑پارکینگ ☐آسانسور ☐انباری   │                                   │
│  ☐فقط مالک                   │   چیپ محله‌ها: اختیاریه ×  قیطریه × │
│  محله (اختیاری): [اختیا…]    │                                   │
│  [ جستجو ]  [ ذخیره ]        │                                   │
├──────────────────────────────┴───────────────────────────────────┤
│ نتایج — ۸۲۲ آگهی، median متری ۱۹م، ۴ مورد مشکوک                   │
│ متری | رهن معادل | ٪بازار | متراژ | اتاق | سن | پ | آ | جدید | Δقیمت │ لینک
│ (مرتب‌سازی با کلیک روی ستون؛ کلیک روی ردیف → پین هایلایت + جزئیات) │
└──────────────────────────────────────────────────────────────────┘
```

- انتخاب محدوده و انتخاب محله **با هم** کار می‌کنند: اگر هر دو خالی → کل شهر (با
  هشدار). اگر فقط محله → مثل الان. اگر محدوده → bbox؛ محله‌های داخلش فقط نمایشی.
- جستجو ممکن است ۱۰-۴۰ ثانیه طول بکشد (تقسیم محدوده + join قیمت دقیق). دکمه
  غیرفعال + نوار پیشرفت متنی («۳ از ۸ خانه…») از طریق polling ساده روی `run_id`.
  بدون WebSocket.
- **وزن‌ها:** پنل یک بخش «وزن معیارها» با چند اسلایدر داشته باشد ولی **در این گام فقط
  مرتب‌سازی تک‌ستونی**. اسلایدرها وقتی موتور امتیازدهی آمد وصل می‌شوند. (جای خالی‌اش
  در UI باشد تا کاربر بداند می‌آید — ولی کد امتیازدهی نه.)

**تأیید:**
- کشیدن مستطیل روی اختیاریه + متراژ ۸۰-۱۵۰ → جدول با تعداد ≈ شمارش دیوار، پین‌ها
  داخل مستطیل.
- کشیدن چندضلعی → هیچ پینی بیرون.
- کلیک روی ستون «متری» → مرتب‌سازی؛ کلیک روی ردیف → پین چشمک بزند.
- اجرای دوم همان محدوده → «جدید: ۰» و ستون Δقیمت پر شود برای آگهی‌هایی که تغییر کردند.
- در موبایل قابل استفاده باشد (فرم زیر نقشه بیفتد) — نه بیشتر.
- چیدمان راست‌به‌چپ سالم باشد: سایدبار سمت راست، آیکون‌ها و فاصله‌ها آینه‌شده،
  اعداد فارسی در ستون‌ها به‌هم نریزد.

## گام ۴ — جزئیات تنبل + موازی‌سازی محدود

- ‏`GET /api/post/{token}`: اگر در `posts.detail_json` و جدیدتر از ۷ روز → از کش؛
  وگرنه `posts-v2/web/{token}` را بگیر، ذخیره کن، برگردان. پنل با کلیک روی ردیف
  آن را می‌خواند و توضیحات، طبقه، سال دقیق، قابل تبدیل بودن را زیر ردیف باز می‌کند.
- **پیش‌واکشی:** بعد از هر جستجو، جزئیات **۲۰ آگهی برتر** در پس‌زمینه با ۳ نخ و
  محدودکننده‌ی نرخ مشترک (حداکثر ۲۵ درخواست در پنجره‌ی اندازه‌گیری‌شده) گرفته می‌شود.
  اول اندازه‌گیری پنجره‌ی ۴۲۹ (اسکریپت یک‌بارمصرف؛ عدد در `DIVAR_API.md`).
- ‏۴۲۹ همچنان با عقب‌نشینی handle می‌شود — ولی استثنا، نه قاعده.

**تأیید:** ۲۰ آگهی برتر بدون کش زیر ۱۵ ثانیه، صفر ۴۲۹. کلیک روی ردیف ۲۱ام → جزئیات زیر ۲ ثانیه.

## گام ۵ — اطلاع‌رسانی تلگرام ✅ ساخته شد

فقط یک‌طرفه. بدون فرم، بدون گفتگو.

- **تصمیم نهایی:** `TELEGRAM_CHAT_ID` هم مثل توکن از `.env` خوانده می‌شود. پس هیچ
  تعامل دوطرفه‌ای لازم نیست و ربات فقط `sendMessage` می‌زند. (طرح اولیه `/start`
  داشت؛ کنار گذاشته شد.)
- در پنل: دکمه‌ی «ذخیره برای اطلاع‌رسانی» بعد از هر جستجو.
- یک job زمان‌بندی‌شده (APScheduler داخل همان FastAPI، هر N ساعت) جستجوهای ذخیره‌شده
  را اجرا می‌کند و **فقط** می‌فرستد:
  - آگهی **جدید** زیر median (پرچم `first_seen` همین اجرا)
  - آگهی‌ای که رهن معادلش **≥ ۵٪ کم شده**
  - (اختیاری) آگهی برتر که **حذف شده**
- هر پیام: یک خط خلاصه + لینک دیوار + لینک به پنل (`/?run_id=…`) برای دیدن در نقشه.
- توکن بات از `TELEGRAM_BOT_TOKEN` (کاربر خودش از BotFather می‌گیرد).

**تأیید:** بعد از دو اجرای زمان‌بندی‌شده با فاصله، فقط تفاوت‌ها پیام شوند؛ اجرای بدون
تغییر → صفر پیام.

## چیزهایی که عمداً در این پلن نیست

امتیاز چندمعیاره و وزن‌دهی (اسلایدرها فقط جای خالی)، تشخیص تکراری، تحلیل متن،
رگرسیون بازار، PostgreSQL، داکر، احراز هویت، استقرار روی سرور. هر کدام بعد از این
پنج گام یک پلن جدا می‌خواهد. با تاریخچه‌ای که از گام ۲ جمع می‌شود، رگرسیون بازار
منطقی‌ترین گام بعدی است.

## ریسک‌ها

- محدودیت نرخ `mapview` ناشناخته است. اول گام ۱ اندازه‌گیری شود؛ اگر سخت‌گیرانه بود،
  مسیر جایگزین `postlist/w/search` + `bbox` (صفحه‌بندی ۲۴تایی) که تست شده کار می‌کند.
- ‏`approximate_location=True` یعنی پین دقیق نیست (دیوار عمداً جابه‌جا می‌کند). فیلتر
  چندضلعی با تلورانس؛ و به کاربر گفته شود پین‌ها تقریبی‌اند.
- قیمت کارت نقشه گردشده است؛ بدون join با لیست، رهن معادل تا ۵٪ خطا دارد. join
  اجباری است نه اختیاری.
- شرایط استفاده‌ی دیوار: استفاده‌ی شخصی روی localhost. پنل را عمومی نکنید.
